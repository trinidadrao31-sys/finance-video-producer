# 总控与状态

每个项目使用独立的项目 ID 和版本记录。按四个阶段记录进度。业务用途、主片型、每镜的人物/人声/图片分别记录。当前 Agent 完成创作并通过执行器提交状态，不另起多 Agent。保持原始 idea、用户批注和终稿。

## 持久状态和固定对话展示

有本地代码能力时，必须在项目目录建立独立 `workflow.sqlite`，使用包内 `scripts/workflow.py`。保存 DB、产物版本文件及真实回执；不要把它放入 Skill 安装目录，不用模型记忆/Todo 作为状态来源。通常按项目目录下 `视频项目/片名/` 的浅层布局保存；先检查已有目录，继续使用原项目，不另建同名副本。

执行顺序：读 `status` → 确定本轮动作 → 登记 `node_start` → 产出及检查 → `apply` 保存事件/真实产物 → `status-card` 显示更新。需要确认才停下来，不为内部节点增加确认轮次。每次恢复、节点产出、卡点、暂停和媒体回执后都展示短状态卡。用户要求查看时可展示完整八节点清单；一般不在每个微小操作后刷屏。必须包含项目、版本、当前节点、产物、卡点、下一步；阶段完成与媒体生成百分比分开，工具没给百分比就不猜。

状态事件及实际 CLI 见 [events.md](references/events.md)。八节点是 N01 需求、N02 素材/能力、N03 文案、N04 分镜、N05 提示词、N06 生成确认、N07 生成/选段、N08 合成/交付，仍合并为下方四步。`artifact` 读取具体节点产物；文件经登记后用宿主交付工具给用户，图片和视频使用宿主媒体卡。

暂停阻止新节点和提交，不代表已取消远端任务；保存回执后可以继续。部分节点重跑先保留旧版、标明下游影响，再执行，不擦掉旧事件。修改规则用 `skill-diff` 查看变化，采用“未来”只影响后续输入，采用“重跑”从指定节点重建；无法自动证明改稿质量，不能把状态逻辑测试当作成片质量证明。

## 先理解这一轮要完成什么

新项目先用一句话写清「观众看完，要看懂哪件事、感到什么或学会什么」。叫 video-intake 从原话中提取可见主体、行为/状态、用户指定的拍法、素材与声音，返回一个主片型建议和依据。总控核对用户目标，提交唯一的 brief.type。已在制作中的项目先辨认本轮是补材料、采纳已展示版本、改某一处、仅导出、还是授权生成；普通反馈沿用已有类型和版本。

在 brief.intent 内保存 audience_goal（观众结果）、requested_type（用户对片型的原话，可空）、type_reason（一句判型依据）、locks（须原样保留的原文或约束）、visual_notes（本次需澄清的表达，可空）。每条 visual_notes 写用户原话、建议拍到的事实、可调整的地方。例如「温馨」已有父亲亲吻宝宝这一动作，可提议父亲轻触额头后停一拍，宝宝仍安睡。故事已有动作时优先细化它。新提议保留为草案，等用户确认创作方案再绑定。对已在制作的项目按需从已有 brief、故事和批注读取信息；无需为新字段重走立项。

每次判断本次改写的范围。成熟输入且动作、节奏、声画和主体都清楚时直接沿用；只有局部适合增强且会改变原意时，保留当前稿，把替代拍法列作用户可选草案；抽象词有明确对象时只具体化相关可见变化；存在两种会拍成不同片子的目标时只问能区分两者的一句。可推断的颜色、光线、摄影偏好作为可改建议。锁定用户指定的台词、音乐、音效、时间、步骤、产品事实和素材身份，保留生产所依赖的段号、有效时长、首尾帧与接缝。UI 步骤与精确对白按执行稿处理；若部分画面适合创意处理，只改指定范围。成熟输入的“沿用”只决定改写范围，后续审查、确认和生成授权照常执行。

## 按拍法自动选编导

用户可以自然描述视频类型，也可以只给 idea。明确要求的拍法优先；“金融、消保、寿险、品牌、高级感、写实”分别可能是业务用途或风格，仍需读 idea。问「观众靠什么看懂这条片」来确定一种主拍法。出现明确冲突时询问创作选择，例如「重点跟随男主经历，还是让他正对镜头教大家辨别？」。系统完成 Skill 映射，用户无需看到菜单。题材、是否有人、是否说话、是否有产品图分别记录。

|brief.type|唯一主编导|用哪种证据判定|
|---|---|---|
|scene|video-scene|人物的行动、决定、关系或反应推动观众理解。男主听屏内专家诱导后转钱、发现损失是情景片。|
|presenter|video-presenter|观众主要跟随一位或多位出镜讲述者听懂观点，插入产品/图卡作佐证。例如员工对镜讲三种诈骗信号。|
|explainer|video-explainer|步骤、图示变化或界面操作本身让观众学会。即使全程有人旁白，逐屏教会关闭免密支付也走此分支。|
|campaign|video-campaign|片子围绕活动揭晓、权益层次、时间与参与动作组织。只在家庭片片尾露出寿险品牌，整片仍按关系驱动判型。|
|showcase|video-showcase|主要任务是让观众看清一件产品的外观、细节或一次实际演示。有人拿起卡片并不自动变成口播。|

第二步写故事和分段均使用这个唯一主编导。混合片给局部镜头标辅助拍法即可。已有稿的必要信息完整时沿用。每个项目持久化 idea、brief、创作方案、待制/已选素材、逐段实际输入、媒体任务和用户确认。

## 四步与确认对象

对话、下载文件及状态记录按 [四步确认单](../四步交付与台词时长.md) 命名。01《需求确认单》首轮给目标时长、口播预算、建议段界及原因；02《分镜脚本确认单》复核逐句话轮，批准后按清单准备资产。03《素材与提示词确认单》先选定《参考资产包》，再逐段展示即将提交的全文和有序输入。04《分段样片确认单》展示真实版本和视听证据，返修回 03，全部采用后明确授权合成并交《成片交付包》。

每段首次、改词重投、原词重抽均走 `segment-text → 在用户对话交付全文 → present_segment → 等用户后续回复 → approve_segment → 高消耗提醒与宿主本批实际生成确认 → claim-video → job_update`。具体预估是可选信息，缺数值或查询失败不单独挂起；真实提交卡点按 [宿主失败分支](references/host.md#开拍前检查与失败分支) 记录。不能仅因内容确认已通过就调用 claim-video。`segment-card` 返回结构化数据供核对；实际向用户交付使用 `segment-text` 原文。用户说“按方案拍”只进入待拍队列。用户说“修 S02”授权准备修订；需要为本次提交另展示确切全文和差异。交付记录包含本次请求摘要、完整正文、实际消息标识；确认引用该消息和后续用户回复标识。缺少消息 ID 的宿主保存真实对话顺序号和正文。实际输入改变后重新取卡、交付和确认。提交结果不明先查原任务。未受影响的已选独立段照常复用。

局部返修循环为 `定位原片缺陷 → repair_plan → repair-text → 实际交付 → present_repair → 用户回复 → approve_repair → claim-repair → job_update → repair_result → 前后对比 → accept_repair`。用户指定的秒点先映射到该段时间，画面问题截取实际原帧并圈定区域，音频问题回听完整词句。按 [局部返修](../video-finish/repair.md) 选择工具和验收方式。原样片保留到新结果被采用。

使用 [宿主能力约定](references/host.md) 和 [四步事件与字段](references/events.md)。Skill 名映射到宿主允许的调用或同名指令正文。若能力未绑定，按阶段交付已完成内容、真实待办。素材目录和客户上传的样片按用户指定用途使用。

## R3 草案与只读边界

查询进度、重发相同需求和导出回执说明不推进业务版本。`plan-card` 可读未采用方案；`draft-export` 将其母稿和逐段草案原样导出，正式 `export` 仍须定稿。方案和资产分别由 `approve_plan`、`start_batch` 记录；视频提交还需要本次 `approve_segment`；编导、自检、工具权限许可与制作回执都不能代替用户内容确认。

原适配的 `register_artifact`、`claim-*`、`job_update`、暂停恢复继续有效，不采用另一版本“忽略这些事件”的说明。新产物首次登记仍保存版本和实际摘要；同版的重复查看、再次下载、快照或状态文字不额外登记。兼容 `summary` 只调用 `status-card`，不引入 `progress.py` 或第二份权威状态。

先读包根 `references/creative-review.md` 做首稿创作验收。仅做展示、审稿或下载时交付草案就结束；禁止因为导出产生文件就自动采用、出图或生视频。
